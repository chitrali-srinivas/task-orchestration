# Deployment V2.1 suites

Checks for `/layouts/deployment-v2-1` in **mock mode** (the default data mode). The browser suites drive the running app
with `puppeteer-core` (already a dev dependency) and a locally installed Google Chrome — nothing is downloaded. Every
request to a Matic API or Firebase host is aborted, and each suite fails if one was attempted. No suite performs a live
mutation. The two node checks run the compiled data layer without a network.

## Run

From `mati-demo/`, with the app running in mock mode (`npm run dev`, default http://localhost:3000):

```bash
# builders / gate / rules (no browser): compile the port-bound modules, then run
npx tsc -p tests/deployment-v2-1/tsconfig.payloads.json
echo '{"type":"commonjs"}' > tests/deployment-v2-1/out/package.json
node tests/deployment-v2-1/check-payloads.mjs

# the live data layer over a stubbed fetch (no network): compile, then run
npx tsc -p tests/deployment-v2-1/tsconfig.live.json
echo '{"type":"commonjs"}' > tests/deployment-v2-1/out-live/package.json
node tests/deployment-v2-1/check-live-api.mjs

# browser suites (each prints PASS / FAIL lines and exits non-zero on a failure)
node tests/deployment-v2-1/e2e.cjs
node tests/deployment-v2-1/ui-refinements.cjs
node tests/deployment-v2-1/dispatch-table.cjs
node tests/deployment-v2-1/table-order.cjs
node tests/deployment-v2-1/column-visibility.cjs
node tests/deployment-v2-1/validation-az.cjs
node tests/deployment-v2-1/boundary-layout.cjs
node tests/deployment-v2-1/boundary-editing.cjs
node tests/deployment-v2-1/noc-image-states.cjs
node tests/deployment-v2-1/noc-footer-layout.cjs
node tests/deployment-v2-1/status-gate.cjs
node tests/deployment-v2-1/actions.cjs
node tests/deployment-v2-1/follow-up.cjs
node tests/deployment-v2-1/boundary.cjs
node tests/deployment-v2-1/camera.cjs
node tests/deployment-v2-1/qa.cjs
node tests/deployment-v2-1/detail-ux.cjs
node tests/deployment-v2-1/media-viewer.cjs
node tests/deployment-v2-1/hover-previews.cjs
node tests/deployment-v2-1/page-density.cjs
node tests/deployment-v2-1/farmer-pagination.cjs
node tests/deployment-v2-1/map-section.cjs
node tests/deployment-v2-1/map-sync.cjs
node tests/deployment-v2-1/boundary-coverage.cjs
```

Settings: `BASE` (app URL, default `http://127.0.0.1:3000`), `CHROME_PATH` (Chrome binary; defaults per OS),
`PROFILE` (scratch profile name — use different names to run suites in parallel). Screenshots land in
`tests/deployment-v2-1/shots/`; the compiled modules in `tests/deployment-v2-1/out/` and `out-live/` (all git-ignored).
`fixtures/clip.webm` (a 20 s generated test clip) stands in for the mock's sample video URL in `media-viewer.cjs`.
**Server.** `.env.local` now puts the `next dev` server on :3000 in LIVE mode, and the suites need mock data: build and serve a mock copy and point the suites at it — `NEXT_PUBLIC_DEPLOYMENT_V2_DATA_MODE=mock npx next build`, then `NEXT_PUBLIC_DEPLOYMENT_V2_DATA_MODE=mock npx next start -p 3210`, and run each suite with `BASE=http://127.0.0.1:3210` (rebuild after a source change). The process environment overrides `.env.local`.
Don't run the suites while `npm run build` is running, and don't edit the app while a suite runs (the dev server
reloads mid-run).

The suites use V2.1's mock switches (URL parameters, mock mode only):

| Switch | Effect |
|---|---|
| `?mockTypes=all` | Adds three rows derived from row 1 for AZ 4 (AWD), AZ 5 (Mati Boost) and AZ 6 |
| `?mockVerifier=nophone` | The mock verifier has no phone number |
| `?mockPermission=view` / `nodelete` / `noawd` | No edit / delete permission · edit without delete · without the AWD / Mati Boost keys |
| `?mockBoundaries=seed` | Saved boundaries on every located plot, except (per row) the last plot of the 2nd dispatch (none) and the first plot of the 3rd (self-crossing) |
| `?mockTrailers=status-required` | A backend that answers nothing to a `getTrailerDetails` without `status`: the per-status fallback is exercised |
| `?mockFail=report-400` | The first report fails like the live dev backend does (simulated HTTP 400 body) |
| `?mockFail=trailers` / `trailers-row2` | The first dispatch read fails once (under the per-status fallback this is only a trace note) · the All tab's second row's dispatch reads fail four times — the status-omitted read and its three fallbacks — so the row shows as failed with Retry |
| `?mockFail=farmer-rows` | The first farmer-rows read fails once (the detail's seed row only, with Retry) |
| `?mockFail=counts` | Every counts read "fails": the rows load and every tab count shows "—" (unavailable, never guessed) |
| `?mockNoc=multi` | The first mock farmer's NOC read returns three photos per AZ (same AZ and status, different images) — the review's Previous / Next; a decision covers every photo of that deployment + AZ |
| `?mockNoc=nourl` | The first mock farmer's NOC read returns, per AZ, its document plus one with `noc: null` (no image link) and one whose link doesn't load |
| `?mockValidation=az` | With `?mockTypes=all`: the per-AZ validation seen live — the first AZ 6 dispatch flagged with the four live AZ 6 messages, the second with no validation sent (`null`); AZ 4 / AZ 6 dispatches without video / source / cluster; one AZ 1 dispatch with its own message; every other dispatch unflagged |
| `?mockValidation=oldest` | Only the 10 oldest pending dispatches (by Submitted on) are flagged (`action_required`, "Video is missing."); every other dispatch has no flag |
| `?mockOrder=unsorted` | The list serves its dispatch rows in a deliberately unsorted order (from both ends of the store inward), reports no sort, and the mock server applies no order of its own |
| `?mockServerSort=none` | The mock server applies no order of its own to a list request without a sort (the store's order) and reports none. By default it answers such a request newest first by Submitted on (oldest first on Pending — the order the live server was seen to use) and reports that as `pagination.sort_by` / `sort_order` (PROPOSED fields) |
| `?mockFail=noc` / `history` | The first NOC read / the first report-history read fails once (the header's "unavailable" NOC, the cards' failed history clock) |
| `?mockFail=geometry` / `geometry-second` | The first / second boundary save fails once |
| `?mockFail=geometry-partial` | The first boundary save that carries several entries applies its first entry, then fails (an outcome the client can't confirm) |
| `?mockMap=dispatch` / `one` / `none` | The detail map draws the record's own dispatch plots, as live mode does (each mock farmer then has its own plots) · only each farmer's first plot · no plot locations |
| `?mockAvatar=wide` / `broken` | Every farmer photo is a 2:1 picture · a photo URL that doesn't load |
| `?mockPlotArea=consistent` / `missing` (comma list) | Every record of each of the first farmer's plots carries the same area (the default mock reuses plot ids with different areas) · the first farmer's first plot has no area on any record |
| `?mockCalArea=` (comma list, the first mock farmer) | `unique`: every plot deployment its own plot_id · `distinct`: each dispatch row's `calculated_area` a fixed value unrelated to its plots' area · `missing` / `invalid` / `zero`: the first dispatch row's `calculated_area` null / "n/a" / 0 · `duplicate` / `conflict`: the farmer read returns the first dispatch row twice (same value / value + 1) · `slow`: the farmer read answers after 8 s |
| `?mockPages=slow` / `slower` | Every table page after the first answers after 2.5 s / 9 s |
| `?mockFail=page` | The first request for a table page after the first fails once (Retry reads it again) |

The map checks need `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY` in `.env.local`, as the app does.

`column-capabilities.cjs` is the table's verified column capability matrix (hide / server sort / server filter / filter UI): the browser suites check the rendered header menus against it and `check-live-api.mjs` checks it against the API contract and the query mapper.
